# Forecasting California's Electricity Demand During Heat Waves

Next-day hourly electricity demand forecasting for the California ISO (CAISO), with a focus on how heat waves change load and where forecasts break down. Classical time-series and gradient-boosted tree models only (no deep learning).

## Why this matters

California's grid operators need accurate next-day demand forecasts to plan generation, imports, storage and reserves. Hot weather pushes demand up sharply because of air conditioning, and that is when forecast errors are most costly. This project builds an operationally realistic forecast (only information available at forecast time) and measures how error changes during extreme heat.

## Questions this project answers

1. Can hourly CAISO demand for the next 24 hours be forecast more accurately than simple seasonal baselines?
2. Which weather and calendar features matter most?
3. How does forecast error change during extreme heat events?
4. What do the largest errors reveal about the model's limitations?

## Models

| Model | Description |
|---|---|
| `baseline_weekly` | Same hour one week earlier |
| `baseline_yearly` | Same hour 52 weeks earlier (keeps the weekday) |
| `baseline_mean7` | Mean of the same hour over the previous 7 days of the same type (weekday or weekend) |
| `ridge` | Ridge regression (RidgeCV) on one-hot calendar and scaled numeric features |
| `lightgbm` | **Primary model.** Gradient-boosted trees, plus 10, 50 and 90 percent quantile models for prediction intervals |
| `sarimax` | Regression with ARMA errors (statsmodels SARIMAX), Fourier daily seasonality, weather and calendar inputs, fit on a limited 56-day window, Gaussian 10 to 90 percent intervals |

Hyperparameters are fixed in `configs/config.yaml` and were **not tuned**. All models use a fixed random seed (42). Not included: XGBoost, Prophet and a 48-hour horizon (optional extras in the original plan).

## Data

| Source | What it provides | Notes |
|---|---|---|
| [EIA Form EIA-930](https://www.eia.gov/electricity/gridmonitor/) via the EIA API v2 | Hourly CAISO demand | Free API key. EIA stamps each reading with the **end** of its hour, so the pipeline shifts stamps back one hour to hour-beginning. Values are the latest revision, not as first published. |
| [Open-Meteo Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api) | ERA5 reanalysis: temperature, apparent temperature, humidity, dew point, wind, cloud cover, precipitation | Gridded reanalysis, **not** station observations. Used for heat-wave labels and the "what actually happened" reference. |
| [Open-Meteo Historical Forecast API](https://open-meteo.com/en/docs/historical-forecast-api) | Archived weather forecasts, same variables | The weather input for training and backtests, so the model sees the kind of input it would have in real use. |
| [Open-Meteo Forecast API](https://open-meteo.com/en/docs) | Live forecast weather | Used only by the dashboard's Live demo tab, and clearly labeled there. |
| Calendar | Hour, weekday, month, weekend, US federal and California holidays, distance to nearest holiday | `holidays` package |

Five locations (Los Angeles, San Diego, Fresno, Sacramento, San Francisco Bay Area) are combined into a population-weighted statewide index. Weights are shares of the **2020 Census** populations of the counties each location represents: Los Angeles, San Diego, Fresno and Sacramento counties, plus four core Bay Area counties (Alameda, Contra Costa, San Francisco, Santa Clara). Other counties (for example Orange, Riverside and San Bernardino) are not represented. See `configs/config.yaml`.

- All timestamps are kept in UTC and converted to Pacific time only for calendar features and charts. Raw and processed data are not committed.

## Forecast setup

- A forecast is issued once per day at **local midnight (Pacific)** and covers the **next 24 hours**.

- **Demand** is known up to the hour just before the origin. Lags are 24, 48, 72, 168 and 336 hours. The code refuses any lag shorter than the horizon. Rolling statistics use only hours before the origin.
- **Weather for the target hours** is the archived forecast, never ERA5. Recent-past weather features also use the archived series.
- **Perfect-weather experiment:** `python -m src.features.build_features --weather era5` writes a separate file with `PERFECT_WEATHER` in its name. It measures how much weather error costs and is never presented as the operational forecast.
- **Real-world timing:** EIA publishes with a delay, so a live run happens a little after midnight. The backtest treats demand through midnight as available at the origin.

### Evaluation protocol

- **Walk-forward validation:** expanding window, refit on a fixed schedule (every 28 days in the full run). Each block is predicted by models trained only on data that ended before the block began. A hard check stops the run if any training target overlaps the test period. The first validation origin is one year after the first feature origin.
- **Final holdout:** the last 8 weeks. Models are trained once on everything before it. Nothing is tuned or selected on it.
- **Metrics:** MAE, RMSE, MAPE, sMAPE, peak-hour MAE (hours starting 16:00 to 21:00 Pacific). For intervals: pinball loss and empirical coverage at 10, 50 and 90 percent.
- **Breakdowns:** overall, by hour, weekday or weekend, season, temperature bin and heat-wave status. The baseline is in every table.

### SARIMAX Walk-Forward Fallback Notes
- During the walk-forward evaluation (1,681 validation origins spanning 21 folds), the SARIMAX model occasionally hits convergence or data constraints and relies on the calendar-only fallback mechanism:
- Out of 1,681 total validation origins, a small number of folds triggered fallbacks (e.g., 5 origins in fold 1, 44 in fold 6, 41 in fold 17, 20 in fold 20), while all checked origins successfully produced fallback forecasts (`0 had no usable forecast`).
- This intermittent fallback behavior is normal for classical time-series models over long evaluation horizons with changing seasonal dynamics.

## Heat-wave definition

- Fixed before any model was evaluated and not tuned afterward.

1. **Daily index:** population-weighted average of each location's daily maximum temperature (local day, ERA5).
2. **Hot day:** index above its 90th percentile for that calendar month.
3. **Heat wave:** 3 or more consecutive hot days.
4. **Headline reporting:** waves in **May to October** (California's cooling season). Because the rule is relative to each month, it also flags unusually warm winter and spring spells. Those are labeled **off-season warm spells**, reported separately and kept out of the headline numbers.

- Heat-wave flags are used for labeling and reporting only, never as model features.

## Features
- 71 features, all available at forecast time: calendar (hour, weekday, month, weekend, holidays, distance to holidays, horizon step); demand lags and rolling mean and standard deviation; weather at the target hours (seven variables at five locations plus the statewide index); cooling and heating degree hours (base 18.3 C), temperature bins and temperature-by-hour interactions; recent heat memory (previous-day maximum, 3-day mean of daily maxima, forecast maximum and mean for the target day). 
- The exact list is saved to `data/processed/feature_list.json`.

## Quickstart

- Developed with Python 3.12.

```bash
git clone <your-repo-url>
cd caiso-demand-forecaster
python -m venv .venv
# Windows PowerShell:  .venv\Scripts\Activate.ps1
# macOS / Linux:       source .venv/bin/activate
pip install -r requirements.txt
Get a free EIA API key at [eia.gov/opendata](https://www.eia.gov/opendata/) and put it in a git-ignored file named `.env` in the project root:
```
EIA_API_KEY=your_key_here
```

Run the whole pipeline, in order:

```bash
python -m src.data.download_eia          # CAISO hourly demand (retries on EIA timeouts)
python -m src.data.download_weather      # ERA5 and archived forecasts, 5 locations
python -m src.data.build_dataset         # clean, validate, merge (refuses to save if checks fail)
python -m src.features.heatwave          # heat-wave labels
python -m src.features.build_features    # forecast feature matrix
python -m src.evaluation.walk_forward    # train, walk-forward validation, holdout (use --fast for a quick preview)
python -m src.evaluation.report          # tables, figures, RESULTS.md, and the blocks of this README
streamlit run src/app/streamlit_app.py  # dashboard
```

- If you have `make`: `make pipeline` runs steps 3 to 7. 
- Tests: `python -m pytest -q` (if pytest crashes on unrelated plugins, use a fresh virtual environment or set `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1`).

## Decision log

- Decisions made before any model error was computed, except where noted.

| Decision | Reason |
|---|---|
| Start in January 2021 | About 5.8 years of history covers several heat seasons with light downloads. |
| Forecast the 24 hours right after the latest demand reading | Matches the "next 24 hours" goal. |
| Archived forecasts as backtest weather | Training and testing see the same kind of input, and results are not inflated by perfect weather. |
| Heat-wave rule: 90th percentile per month, 3+ days | Pre-specified. A 95th percentile gives very few events in under six years. |
| Headline heat waves limited to May to October | The month-relative rule flags warm winter spells that carry little cooling load. First set to June to September, widened once after real October heat waves turned out to sit inside the planned holdout. Final. |
| Shift EIA timestamps back one hour | EIA documents readings as hour **ending**. |
| Trim demand hours with no weather at the edges | The shift above put one demand hour before the weather starts. Gaps in the middle still fail the checks. |
| Do not impute missing demand | A handful of hours out of about 51,000. Affected rows are dropped. |
| Census-based weights | Replaced earlier rough placeholders with 2020 Census county populations. Done before any model was trained. |
| Fixed, untuned model settings | No hyperparameter search, so nothing was fitted to the validation or holdout periods. |
| SARIMAX as regression with ARMA errors and Fourier terms | A seasonal-difference SARIMAX on hourly data is too slow to refit regularly. This version refits in seconds. |

## Known limitations

- **ERA5 is gridded reanalysis**, not station observation, and five points stand in for an entire state. Census weights cover only the counties listed above.
- **EIA revises past values.** Only the latest version of each hour is available, so backtests are somewhat more optimistic than live use.
- **Archived forecasts are not true day-ahead forecasts.** Open-Meteo builds the archive from the early hours of each model run, so it behaves like a short-lead forecast. Real midnight-issued weather error would probably be a little larger.
- **Heat-wave labels use full-period percentiles.** Fine for labeling, but the labels know about the whole period. They are never model inputs.
- **Few extreme events.** The final holdout contains very few heat-wave days, so most heat-wave evaluation comes from the walk-forward period.
- **Untuned models.** Better settings may exist. SARIMAX intervals are Gaussian and may be too narrow or too wide in extremes.
- Missing demand hours are not filled, so a small share of forecast rows are dropped. Around daylight-saving changes, one forecast hour is skipped or duplicated per year.
- The Live demo is a demonstration, not an operational system.
